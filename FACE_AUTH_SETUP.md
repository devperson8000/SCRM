# Test branch: password and face login

This branch replaces the old password-only gate. It does not change main until
merged. Test it with a **separate database and preview deployment**, not your
production authentication database. Existing password-only cookies do not grant
access. There is no built-in admin password or camera bypass.

The camera and Admin Panel are part of this website. Recognition runs on your
own backend using bundled open-source models; there is no external biometric
service. A PostgreSQL database is required for approvals and sessions.

## Quick local test

Prerequisites: Node 22.23.3 or newer Node 22, pnpm 10.26.1, Docker with Compose,
a webcam, and a Chromium/Firefox/Safari browser with camera permission.

```sh
git switch test/face-login
pnpm install --frozen-lockfile
pnpm auth:local
pnpm auth:dev
```

`auth:local` starts PostgreSQL on localhost:5432, asks you to choose separate
normal and admin passwords (at least 12 characters), generates private keys and
an initial setup secret, and migrates the database. Typed secrets are hidden.
It writes `.env.auth`, `.env.auth.db`, and `.env.auth.setup-secret.txt`, all
excluded from Git. Do not send these files to anyone or paste them in chat.
The script refuses to overwrite existing authentication configuration.

Open **http://localhost:4141** on the same machine (not 127.0.0.1; the configured
origin must match exactly). Camera permission requires HTTPS or localhost.

1. Enter the **admin password** you chose. Select **Enroll administrator face**.
   Read your one-time secret locally from `.env.auth.setup-secret.txt`, enter it,
   consent to storage, and follow the camera instructions. The setup secret is
   not your password. Initial setup can succeed only once, transactionally.
2. Save the eight recovery codes shown in the **Admin Panel**. They are shown
   once. Each code, together with the admin password, can start replacing the
   admin face; starting a recovery scan consumes that code even if cancelled.
3. In another browser profile/private window, have a **different test person**
   enter the normal password. Select **Enrol your face**, enter a name, consent,
   and complete the scan. It must show **Awaiting approval**, without Scramjet.
4. In the Admin Panel, refresh requests and approve that person. Names are
   self-reported: confirm who requested access before approving.
5. The user checks approval, returns to login, enters the normal password and
   completes a **new** scan. Only then does Scramjet open.
6. Test **Reject**, **Revoke access**, and **Delete enrollment**. Revocation
   invalidates existing sessions immediately at the API, and existing Wisp
   connections are disconnected by their next check (within 30 seconds, plus
   bounded database request time). Revoked users cannot reconnect.
7. Log out with **Lock Admin Panel** or **Lock workspace**. After normal admin
   setup, later admin logins require the admin password plus that enrolled face.

The initial design separates admin and user identities: the admin face cannot
also enroll as an ordinary user. An admin cookie never implicitly grants proxy
access. Use another consenting person to exercise user approval in this version.

A scan has three steps: face forward, turn toward one preview edge, then the
other edge. Keep one well-lit face close to the camera. Two images are sampled
at each step. Camera tracks stop after capture, cancellation, or navigation.
If the browser denies permission, allow it in site settings and retry.

Keep the database volume between runs. Restart with `pnpm auth:dev`; do not run
bootstrap repeatedly or discard your keys. To stop just the test database:

```sh
docker compose --env-file .env.auth.db -f compose.auth.yaml stop
```

## Existing/self-hosted database

Instead of `auth:local`, run `pnpm auth:config` and provide your application
origin and PostgreSQL URL in the hidden prompts, then:

```sh
node --env-file=.env.auth scripts/auth-migrate.ts
pnpm auth:dev
```

Use `.env.auth` only on your private machine. For hosting, enter its values in
secure deployment settings. Password hashes use salted scrypt. Templates use
AES-256-GCM with an independent encryption key and per-user associated data.
Never put actual passwords, camera captures, setup secrets, recovery codes,
DATABASE_URL, or encryption keys into Git, build arguments, or client variables.

## Vercel preview and persistent Wisp backend

Deploy **test/face-login** as a preview with its own PostgreSQL database. Configure
an exact stable preview HTTPS origin. Do not use wildcard origin authorization.
Supply these server-only variables, generated by `pnpm auth:config`:

| Variable                 | Purpose                                                                                                            |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| `DATABASE_URL`           | Durable PostgreSQL database; use TLS according to your database provider, keeping certificate verification enabled |
| `AUTH_ORIGIN`            | Exact HTTPS preview origin, without trailing slash                                                                 |
| `ACCESS_PASSWORD_HASH`   | Salted scrypt hash of normal password                                                                              |
| `ADMIN_PASSWORD_HASH`    | Salted scrypt hash of a different admin password                                                                   |
| `ADMIN_SETUP_TOKEN_HASH` | SHA-256 hash of the one-time high-entropy setup secret                                                             |
| `FACE_TEMPLATE_KEY`      | 32 random bytes encoded as 64 hex characters                                                                       |
| `SESSION_SECRET`         | Separate 32-byte random secret, hex encoded                                                                        |

The existing `WISP_SHARED_SECRET` and `WISP_SERVER_PUBLIC_URL` settings are still
required for deployed proxy operation. Use `render.face-test.yaml` to create a separate Render test backend tracking
`test/face-login`; do not change your production service to that branch.
The Wisp backend must use the **same test
database and authentication settings**, plus the same `WISP_SHARED_SECRET`.
Database connections use PostgreSQL's normal TLS configuration; do not disable
certificate verification to fix deployment errors.

Run the schema migration against the preview database before accepting logins.
The Vercel install command runs `pnpm auth:build` after dependencies are installed,
so server modules exist before function tracing. The build command repeats it
before Vite. This generates an
ignored `api/_lib/auth-runtime.js` because Vercel does not rewrite TypeScript
import extensions. The build copies face models and WASM files into the ignored regular directory
`api/_lib/face-assets/`; the function includes that directory instead of
pnpm-symlinked `node_modules` paths. Models come from pinned `@vladmandic/face-api@1.7.15`, and the server
checks their committed SHA-256 checksums before loading.

The face-login function has a 60-second execution budget. Local WASM load plus
blank-image detection was approximately 0.5 seconds here, but **Vercel cold
starts, complete multi-image recognition, package tracing, memory and CPU limits
must be checked on your preview**. A production deployment has not been made by
this change. Use `pnpm auth:benchmark` on the actual target. Do not enable access
without required files or fall back to client-side match assertions. If your
hosting plan cannot run inference, move that same server verifier to your own
persistent backend before enabling the feature; a separate recognition worker
is not implemented in this branch.

Migration changes the Wisp token format: tokens now bind to an approved user
session and expire after 60 seconds. Deploy the updated Wisp backend first
(it rejects old tokens), then the preview frontend/functions. Drain old Wisp
instances/connections. Do not mix old password-only backends with these APIs.
Remove old deployments from public access if they still grant password-only
sessions. Pending template expiration runs in the persistent Wisp process and
dev server every minute, and during approval/scan operations. If neither process
runs, schedule `AuthService.cleanup()` yourself before promising time-based
physical deletion in a serverless-only deployment.

## Automated verification

Use a disposable PostgreSQL database, not one with real enrollment records.
`tests/auth.test.ts` truncates authentication tables in that database.
`tests/browser/auth.browser.ts` uses its own `scrm_browser` schema and starts its
own development server on port 4143. Set `TEST_DATABASE_URL` securely in your
shell; do not put credentials on the command line or into source.

```sh
pnpm auth:build
pnpm auth:typecheck
pnpm auth:test
pnpm auth:test:browser
pnpm auth:benchmark
pnpm exec vite build --outDir /tmp/scramjet-face-preview-build
```

The browser test needs Chromium (`/usr/bin/chromium` by default; override
`CHROMIUM_PATH`) and a disposable database. It uses a fake camera and an
explicitly injected test-only verifier in the test process. **It verifies
password routing, camera UI, pending status, approval and revocation, not human
face recognition or anti-spoofing.** Application deployments have no such
verifier override or success fallback. Unit tests separately check image
validation, motion order, encryption/session authorization and model loading.

## Security and biometric limits

This is webcam-based face matching, **not Apple Face ID or certified liveness**.
Randomized head turns reject a simple still-photo scan, but are not proof against
replayed video, virtual cameras, deepfakes or a malicious client. The matching
threshold is conservative (Euclidean distance 0.48 on 128-value embeddings) and
requires testing with consenting people across lighting and cameras. No human
accuracy, false-acceptance rate or spoof-resistance claim has been established.
Treat this branch as an experimental test workflow, not a production security
upgrade until those checks and deployment checks are complete. Passkeys remain
the recommended strong authentication factor if protecting sensitive access.

Only server-computed embeddings are trusted. Raw frames are processed in memory
and not saved; encrypted templates are stored for pending/approved enrollments.
Reject/revoke/delete removes templates. Pending enrollments expire after seven
days. Ordinary users cannot list other users or read stored biometric data. The
Admin Panel never returns templates. Admin sessions expire after 30 minutes;
ordinary sessions after 12 hours, with live database approval checks. Password,
scan and enrollment throttles are database-backed across instances. Keep backup
and encryption-key access restricted; deletion from live tables cannot erase
copies in your database backups automatically.
